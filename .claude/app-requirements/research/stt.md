# Research: stt

> Snapshot from 2026-10-14, written by Claude's research agents for the app spec (`../CLAUDE.md`). Each finding lists its sources and a confidence level. Recheck anything time-sensitive (versions, prices, store policies) before acting on it.

## Summary
Use jamsch's expo-speech-recognition for v1. It is MIT-licensed, at 57.1.1 (published 2026-10-08), and its version numbers now follow the Expo SDK (57.x is for SDK 57 / RN 0.86, the current stable Expo). It gets about 758k npm downloads a week and needs a development build. It supports live partial results, continuous mode, contextualStrings (word hints for proper nouns), word segments with millisecond timings, and on-device mode. On iOS it wraps only SFSpeechRecognizer and does not expose iOS 26 SpeechAnalyzer/SpeechTranscriber. The SpeechAnalyzer path therefore needs a small local Expo module in Swift, a good v1.5 task. The main privacy catch: the library's requiresOnDeviceRecognition is quietly ignored when the device can't do on-device recognition. On iOS it is only set if supportsOnDeviceRecognition is true. On Android 12 and older it falls back to the network recognizer with a "prefer offline" flag that Android says may have no effect. So the app must check on-device support itself before starting, or the "raw audio never leaves the device" rule can break. Apple's server-side limits (1-minute audio cap, daily quotas) do not apply on-device, which matters because recite cards run up to 450 words (about 3 minutes). Speech recognition is broken in the iOS 26.4+ and iOS 27 simulators (open issue #145), so STT must be tested on Thomas's iPhone. For later open-source engines, sherpa-onnx streaming zipformer (Apache-2.0) fits best: a small English encoder of about 41 MB (int8), true streaming, and hotword boosting for names like Zebulun. Whisper-family models and Moonshine can invent text during pauses, and reciters pause a lot. For grading, Microsoft's own continuous-mode pronunciation samples tag omissions and insertions with a plain difflib sequence diff. The recommended design goes further: one engine interface that turns every engine's output into numbered segments, plus a pure-TypeScript aligner. The aligner compares each segment to a window of the passage around the current position, uses sound-alike matching (Double Metaphone), expands numbers, detects jumps and repeats, and suggests an FSRS grade using the same thresholds as the sequence-v2 type mode.

Since v56.0.0 (2026-05-17) its version matches the Expo SDK: use ^57.0.0 for SDK 57 and 56.x for SDK 56. The sdk-54/sdk-55 npm tags point to 3.1.3. ## recommendations
- STT INTERFACE (src/stt/types.ts). Every engine implements one interface: `interface SttEngine { id: 'ios-sfspeech'|'ios-analyzer'|'android-ondevice'|'sherpa'|'replay'; probe(locale): Promise<{available:boolean; onDevice:boolean; modelInstalled:boolean; reason?:string}>; prepare(locale, onProgress?): Promise<void>; start(o:{locale:string; biasPhrases:string[]; sessionId:string}): Promise<void>; stop(): Promise<void>; abort(): void; onHypothesis(cb:(h:Hyp)=>void): Unsub; onLevel(cb:(db:number)=>void): Unsub; onError(cb): Unsub }` with `type Hyp = { sessionId; segmentId:number; text:string; isFinal:boolean; alts?:string[]; words?:{w:string; startMs?:number; endMs?:number}[]; at:number }`. Each adapter must emit 'replace the current segment' events: a new partial for segment N replaces the previous one, isFinal freezes segment N, and the next speech becomes N+1. This one rule absorbs iOS's growing transcript, the iOS 18 reset-after-pause bug, Android's chunked sessions, and SpeechAnalyzer's tentative-then-final results. Add a 'replay' engine that plays back logged Hyp JSON so the aligner can be tested in Jest/Vitest without a microphone.
- PRIVACY CHECK BEFORE STARTING (inside the interface, not the UI). iOS: start only if ExpoSpeechRecognitionModule.supportsOnDeviceRecognition() is true. Android: start only if API >= 33 and getSupportedLocales() lists en-US as installed; otherwise offer androidTriggerOfflineModelDownload(). If either check fails, voice mode is off and the card falls back to type mode / self-grading. Never call start() with requiresOnDeviceRecognition unchecked. Never set recordingOptions.persist.
- v1 ENGINE (personal use and church beta): expo-speech-recognition@^57.1.1 with {lang:'en-US', interimResults:true, continuous:true, requiresOnDeviceRecognition:true, addsPunctuation:false, maxAlternatives:3, contextualStrings: properNouns(passage).slice(0,100), iosTaskHint:'dictation', volumeChangeEventOptions:{enabled:true, intervalMillis:100}}. Limit each session to one card (≤450 words, ~3 min). Stop on card flip, when the app goes to the background, and after ~8 s of silence. Use expo-keep-awake only while recording.
- v1.5 iOS ENGINE: a local Expo module (npx create-expo-module@latest --local → modules/speech-analyzer, Swift) wrapping SpeechAnalyzer. Configure SpeechTranscriber with reportingOptions [.volatileResults] and attributeOptions [.audioTimeRange], fall back to DictationTranscriber when SpeechTranscriber.isAvailable is false, install models via AssetInventory, and call prepareToAnalyze when the card opens. Pick the default transcriber with an A/B test on Thomas's recorded recitations: DictationTranscriber accepts contextualStrings, SpeechTranscriber does not but uses the stronger model. This path needs only NSMicrophoneUsageDescription. Use it on iOS 26+ and keep the SFSpeechRecognizer adapter for iOS 16.4–25.
- LATER ENGINE (Android ≤12, non-Google devices, consistent behavior across platforms): sherpa-onnx streaming zipformer en-20M int8 (~45 MB total) with hotwords for proper nouns via modified_beam_search. Prefer a small custom Expo module over sherpa-onnx's official Kotlin/Swift APIs (Apache-2.0) rather than react-native-sherpa-onnx, because of its LGPL FFmpeg parts and young maintenance. Download the model on first use, not bundled. Keep Whisper and Moonshine out of grading paths because they can invent words during pauses.
- PREPROCESSING THE PASSAGE (once per card build, cached in SQLite). Split the BSB text into words; each token stores {display, norm, phon:[dm1,dm2], verse, lineIdx, aliases[]}. norm = lowercase, strip punctuation, curly quotes→ASCII, split em-dashes and hyphens (keep hyphenated words as an alias group). Expand numerals into word sequences with to-words/number-to-words ('46,500' → 'forty six thousand five hundred') and also accept the digit form. Fold 'LORD' to 'lord'. Proper-noun list = capitalized words not at sentence start plus a curated list (Zebulun, Melchizedek…), giving biasPhrases (≤100, 1–2 words each). Treat a spoken reference ('Matthew five three') as an optional prefix that costs nothing.
- MATCHING A SEGMENT TO THE PASSAGE (pure TS, src/recite/align.ts). Keep `frontier` = the furthest passage word confirmed by final segments. On every Hyp, normalize the current segment H the same way and align it against window W = ref[frontier−15 .. frontier+40]. Use a semi-global weighted edit distance: H must be used fully, W's ends are free, plus a penalty of 0.15×|start−frontier| (capped) so the match prefers to continue where the user left off. Substitution costs: 0 exact or alias or homophone with the same Double Metaphone code; 0.3 Levenshtein ratio ≥0.8 ('close'); 1.0 otherwise. Also allow merging 2 words into 1 or splitting 1 into 2, compared by joined sound code ('Melchi zedek'). Skipped passage word = 1.0, extra spoken word = 0.6. Cost is about |H|×|W| ≤ 60×55 cells per partial, trivial in JS. If the window match is poor (<50% matched), run a Smith–Waterman local search of the last 6 spoken words over the whole passage. A run of ≥4 matches elsewhere moves `frontier`: jumping ahead marks the skipped words missed; jumping back counts as a repeat with no penalty, and the later attempt overwrites those words. When a word is unmatched, check maxAlternatives and use an alternative only if it fills exactly that slot.
- WORD STATES AND STABILITY. States per passage word: pending | tentative (matched by a partial) | matched | close | missed | hinted, plus an insertion count between words. Draw tentative words in a light tint. Lock them when their segment becomes final, or when they stay unchanged for 3 partials / 1.2 s. The karaoke marker sits at the furthest locked match and only moves backward on a detected repeat. Don't use engine confidence for live coloring (iOS gives 0 on partials; Android gives -1). After about 4 s with no new match while the volume meter shows silence, offer a first-letter hint (counts as 'hinted').
- GRADING (mirrors sequence-v2 §7 type mode). Suggest Again if a hint was used or ≥2 words were missed. Suggest Good if 0 missed and ≤1 close. Otherwise suggest Hard. Never auto-suggest Easy. The user confirms with one tap and can always override, since STT errors are not user errors. Homophone and sound-alike matches count as correct; proper nouns get the 'close' threshold relaxed to a ratio of 0.7.
- TRAIL STORAGE (local SQLite, no audio). One row per attempt: {cardId, attemptAt, durationMs, engineId, engineVersion, states:'MMCMXMH…' (one char per passage word), insertions:'0,0,1,…', suggestedRating, finalRating}. Store engineId and version so progress views don't compare results across engine changes. Sync only the states string if groups need it, and declare it on the privacy label. While Thomas is the only user, log Hyp streams as text-only JSON fixtures for regression tests. Don't collect beta testers' transcripts without explicit opt-in.
- ACCESSIBILITY. Never rely on color alone (WCAG 1.4.1): matched = solid fill, close = dotted underline, missed = strikethrough or outline. Use a colorblind-safe pair (e.g., blue/orange) rather than green/red for the 'spotty to green' progress view. ## gotchas
- requiresOnDeviceRecognition is silently ignored when unsupported (iOS sets it only if supportsOnDeviceRecognition; Android ≤12 falls back to the network recognizer with a best-effort 'prefer offline' flag). Check yourself first or audio can leave the device.
- Speech recognition is broken in the iOS 26.4+/27.0 simulators (issue #145), and SpeechTranscriber.isAvailable is false in the simulator. Test all STT on the physical iPhone with a dev build; Expo Go won't work.
- Transcript behavior varies by OS: iOS ≤17 growing transcript, iOS 18 reset-after-pause bug, Android chunked sessions, SpeechAnalyzer tentative/final ranges. Build the aligner around per-segment replace semantics, never around 'the full transcript so far'.
- Contextual biasing can hide real mistakes: feeding the whole verse as contextualStrings or hotwords pushes the recognizer toward the correct answer and flatters the user. Bias only proper nouns and rare words (Apple: ≤100 phrases, 1–2 words).
- Recognizers with a language model (Whisper, Moonshine; somewhat Apple's too) may 'autocorrect' toward familiar wording or fill pauses with invented text. Reciters pause, so prefer transducer models (sherpa zipformer) for any open-source grading engine.
- SpeechTranscriber does not support contextualStrings (only DictationTranscriber does); proper nouns like 'Melchizedek' will often come back as several words, so the aligner needs 2-to-1 / 1-to-2 matching by sound.
- Confidence values are not usable for live coloring: iOS gives 0 on partials, Android segments give -1, and Android word timings come only in final results, only on Android 14+ on-device.
- Android 13+ plays a beep on start and stop unless continuous mode is used; Android 12 and older has no continuous or on-device mode in this library (~30% of Android devices worldwide, July 2026).
- The plugin's default permission text is generic ('Allow $(PRODUCT_NAME) to use speech recognition.'); vague purpose strings risk App Review rejection. Write specific ones.
- Starting recognition switches the iOS audio session to playAndRecord/measurement, which can interrupt or duck other audio (e.g., a future 'listen to the passage' feature). Restore the session on stop.
- SFSpeechRecognizer's on-device mode depends on the system's dictation assets; if isAvailable or supportsOnDeviceRecognition is false, the user may need to enable Dictation in Settings. DictationTranscriber on iOS 26+ avoids this.
- react-native-sherpa-onnx bundles LGPL FFmpeg/Shine, which adds licensing work for App Store binaries; upstream sherpa-onnx is Apache-2.0.
- expo-speech-transcriber looks like the SpeechAnalyzer answer but hasn't been published since Dec 2025 and hardcodes en_US; don't build on it.
- Engine changes shift accuracy. Store engineId and version with each trail, or 'progress' charts will show improvements that came from the engine, not the user.

## open_questions
- Which iPhone model and iOS version is your test device? It decides whether SpeechTranscriber is available (reportedly iPhone 12+) and whether the SpeechAnalyzer path can be tested at all.
- What minimum Android version should voice mode support: 13+ only (on-device available, ~70% of devices) with type mode below that, or invest early in sherpa-onnx to cover Android 12 and older?
- Should a voice-derived grade be applied to FSRS automatically or always shown as a suggestion the user confirms? (The recommendation is suggest-and-confirm.)
- Should recitation trails sync to the server (for group progress / multi-device), or stay device-only? This changes the privacy label and backup design.
- How lenient for proper nouns and homophones: count 'close' as fully correct for grading, or only for coloring?
- If on-device recognition is unavailable on a user's device, is a clear opt-in to network recognition ever acceptable, or does 'raw audio never leaves the device' mean voice mode is simply off there? (The current decision implies off.)
- Should the trail show tentative (partial-result) matches live, or only locked matches? This trades a snappier karaoke feel against visible flicker when the recognizer changes its guess.
- Will non-English or other-translation support matter before public launch? It affects AssetInventory locale reservations and the choice of open-source model.
