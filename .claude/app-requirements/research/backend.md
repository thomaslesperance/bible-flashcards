# Research: backend

> Snapshot from 2026-10-14, written by Claude's research agents for the app spec (`../CLAUDE.md`). Each finding lists its sources and a confidence level. Recheck anything time-sensitive (versions, prices, store policies) before acting on it.

## Summary
Everything here was checked against official sources on 2026-10-14. The GCP stack you already chose costs about $10/month in production at 10, 100 and 1,000 users. Almost all of that is one Cloud SQL db-f1-micro instance ($0.0105/hr ≈ $7.67/mo, plus 10 GiB SSD ≈ $1.70 and backups ≈ $0.10–0.30). Cloud Run (request-based billing; free tier of 180k vCPU-s, 360k GiB-s and 2M requests a month), Firebase Auth / Identity Platform (free up to 50K monthly active users), Secret Manager, Artifact Registry and logging all stay inside their free tiers at this scale. The biggest Terraform foot-gun: on PostgreSQL 16 and later, Cloud SQL defaults to Enterprise Plus, and shared-core tiers then fail unless you set `edition = "ENTERPRISE"`. Shared-core instances also have no SLA. Current tools: Terraform 1.16.6 with google/google-beta 8.7.0. Firebase project and app resources are still beta-only, so they need `google-beta`. Firebase's own guide still pins `~> 6.0`, which is stale. Configuring Auth in Terraform turns on Identity Platform and needs the Blaze plan. For sync, a custom append-only event log fits better than PowerSync, ElectricSQL or Firestore: client-generated UUIDv7 ids, idempotent `INSERT ... ON CONFLICT DO NOTHING`, and pulls by a per-user server sequence number. ts-fsrs 5.4.2 has `reschedule(card, reviews)` for rebuilding card state from logs. For the coding agent, the safe pattern is separate dev and prod projects plus a dev-only service account that Claude Code borrows through gcloud impersonation (acting as that account using Thomas's login, no key file); that account holds no roles in prod. Prod deploys run only from GitHub Actions via Workload Identity Federation, with no JSON keys. Stripe is not needed when the app just opens the church's existing giving page outside the app. Apple allows free apps to collect donations only outside the app (e.g. Safari). Google Play forbids its own billing for tax-exempt donations, and the donation must unlock nothing in the app. Phase 1 (personal use) needs no cloud at all, because the app is local-first.

## Findings
- **[high]** Cloud Run request-based billing (us-central1, Tier 1): $0.000024/vCPU-s active, $0.0000025/GiB-s, $0.40 per million requests. The free tier per billing account is 180,000 vCPU-s, 360,000 GiB-s and 2M requests a month. Min-instance idle time costs $0.0000025/vCPU-s; idle instances that are not min instances cost nothing.
  - Instance-based billing costs $0.000018/vCPU-s and $0.000002/GiB-s, with a free tier of 240k vCPU-s and 450k GiB-s but no request allowance. Billing rounds up to 100 ms. 1 GiB/month of North America egress is free. Keeping 1 warm instance (1 vCPU, 512 MiB) costs about $6.57 CPU + $3.29 memory ≈ $9.86/mo at list price; how much the free tier offsets this is unverified. Requests denied by IAM are not billed.
  - sources: https://cloud.google.com/run/pricing
- **[low]** Cold starts at min-instances=0: Google publishes no Node.js figure. Expect roughly 1–3 s for a small bundled Node/Hono or Fastify service, plus Cloud SQL connector startup.
  - Official guidance: queued requests wait up to 3.5× the average startup time or 10 s, whichever is greater. Startup CPU boost (`startup_cpu_boost`) helps, module loading dominates Node startup, image size does NOT matter because images are streamed, and default concurrency is 80. No Hono-vs-Fastify cold-start benchmark exists. Because the app is local-first and syncs in the background, users will rarely see a cold start; sign-in and the group dashboard are the exceptions.
  - sources: https://docs.cloud.google.com/run/docs/tips/general
- **[high]** Smallest Cloud SQL for PostgreSQL: db-f1-micro (shared vCPU, 0.6 GiB RAM) at $0.0105/hr ≈ $7.67/mo. db-g1-small (1.7 GiB) is $0.035/hr ≈ $25.55/mo. SSD is $0.000232877/GiB-hr ≈ $0.17/GiB-mo; used backups are ≈ $0.08/GiB-mo. Shared-core instances are not covered by the Cloud SQL SLA.
  - High availability doubles the instance price (f1-micro HA $0.021/hr). Idle IPv4 costs $0.01/hr, so stopping an f1-micro saves almost nothing ($0.0105 vs $0.01 an hour): delete unused instances instead. Default max_connections is 25 for the ~0.5 GB tier and 50 for 1.7 GB. Extended-support fees apply only to end-of-life major versions; PG14 reaches EOL on 2026-11-12. Cloud SQL supports PostgreSQL 12–18. The free trial (30 days, Enterprise Plus 8 vCPU/64 GB, new project only, no backups) is useless for long-term hosting.
  - sources: https://cloud.google.com/sql/pricing, https://docs.cloud.google.com/sql/docs/postgres/flags, https://docs.cloud.google.com/sql/docs/postgres/free-trial-instance, https://www.postgresql.org/support/versioning/

  - From the Terraform `google_sql_database_instance` docs: Enterprise Plus supports only `db-perf-optimized-N-*` tiers. Also useful: `connector_enforcement = "REQUIRED"` rejects direct connections; `deletion_protection_enabled` protects across API, gcloud and console; `database_version = "POSTGRES_18"`.

- **[medium]** Custom sync design. Events are append-only and carry a client-generated UUIDv7. Upload is idempotent via `ON CONFLICT (id) DO NOTHING`. Pull uses a per-user server sequence cursor (never a timestamp). FSRS state is rebuilt with ts-fsrs `reschedule(card, reviews)`, so merges never conflict.
  - Push (POST /v1/sync/push): inside one transaction, run `SELECT event_seq FROM users WHERE id=$1 FOR UPDATE`, drop ids that already exist, insert the new events with seq = event_seq + row_number, then bump users.event_seq. Locking the user row orders concurrent pushes, so a cursor can never skip an event that commits late (a single global serial can). Pull (GET /v1/sync/pull?after=<seq>&limit=500): returns events plus `next`/`has_more`. Client keeps an outbox (`synced_at IS NULL`) and inserts pulled events with ON CONFLICT DO NOTHING. It then re-derives state for affected card_keys, sorted by (reviewed_at, id), using pinned FSRS params and ts-fsrs version. Store the post-review snapshot (due, stability, difficulty) in `client_meta` so normal devices don't have to replay. Undo is an 'undo' event, never a DELETE. Small mutable records (custom outlines, settings) use last-writer-wins with a `version` column. Libraries: uuid 14.0.3 has `v7()` and needs `react-native-get-random-values` 2.0.0 imported first; ts-fsrs 5.4.2 (FSRS-6) has `enable_fuzz`, and fuzz makes replay non-reproducible unless you disable it or keep the stored due date.
  - sources: https://raw.githubusercontent.com/open-spaced-repetition/ts-fsrs/main/packages/fsrs/README.md, https://github.com/open-spaced-repetition/ts-fsrs, https://github.com/uuidjs/uuid, https://www.postgresql.org/docs/18/functions-uuid.html

## gotchas
- This is the part people get wrong: on PG16 and later, Cloud SQL defaults to Enterprise Plus, so a db-f1-micro Terraform config without `edition = "ENTERPRISE"` fails.
- Shared-core Cloud SQL (f1-micro / g1-small) has no SLA, and f1-micro allows only 25 connections by default. Cap Cloud Run max instances × pool size accordingly.
- Stopping a Cloud SQL instance doesn't save money at this size: the idle IPv4 charge ($0.01/hr) is almost the f1-micro price ($0.0105/hr). Delete unused dev instances instead.
- Firebase's Terraform guide pins google-beta `~> 6.0`, but the current version is 8.7.0. Firebase project, app and App Check resources are still beta-only and need `provider = google-beta`.
- Configuring Auth via Terraform upgrades the project to Identity Platform and needs the Blaze plan (billing linked). Whether the upgrade can be reversed is unverified.
- Terraform state stores the Identity Platform `client.api_key` (and any secret you pass) in plain text. Treat the state buckets as secrets.
- `google_cloud_run_v2_service.deletion_protection` defaults to true, so `terraform destroy` fails until you flip it. CI image deploys cause Terraform drift unless you ignore the image field.
- Two credentials can't share the Authorization header: if Cloud Run IAM is left on, the Firebase ID token conflicts with the IAM bearer token. Set `invoker_iam_disabled = true` and let Firebase tokens do authentication.
- A timestamp- or UUIDv7-based pull cursor skips late offline uploads, and even a global bigserial can commit out of order. Use a per-user seq assigned under the user row lock.
- Device clocks drift, so replay ordering uses (reviewed_at, id). ts-fsrs `enable_fuzz` adds randomness, so either disable it or treat the stored due date as the source of truth; pin ts-fsrs version and params for replays.
- The uuid package's v7 needs crypto.getRandomValues on React Native: import `react-native-get-random-values` before uuid.
- Budgets only alert, hours late. Spend Caps are Preview, cover one project + one service, don't cover Cloud SQL, and must be lifted by hand.
- Workload Identity Federation without an attribute condition lets any GitHub repo in. GitHub uses one issuer for everyone, so always restrict by repository_id/owner_id.
- The Firebase Admin SDK doesn't support direct Workload Identity Federation. CI jobs using firebase-admin must use the `service_account` (impersonation) form.
- IAM deny policies effectively need an Organization (Deny Admin is granted at org level). Without one, isolation rests on separate projects plus a service account that has no prod roles.
- Donation link: the app must stay free, the donation can't unlock anything (badges, plant growth), and the link should open outside the app (Safari or an external browser), not an in-app webview.
- Apple: offering Google sign-in requires an equivalent privacy-focused option (Sign in with Apple). Supporting accounts requires in-app deletion, and revoking Apple tokens needs the Services ID + key configured.
- `verifyIdToken` doesn't check revocation by default; `checkRevoked=true` adds a network call. Use it only on sensitive endpoints.
